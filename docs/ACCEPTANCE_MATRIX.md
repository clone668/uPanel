## 0. 怎么读，以及三条硬规矩

**状态只有三种**，没有第四种：

| 状态 | 意思 |
|---|---|
| **已验** | §19 那一行描述的**全部**子句都有真实 Ubuntu 客机上的读数（不是单测、不是宿主、不是 mock） |
| **部分** | 有真机读数，但那一行里**至少一个子句**只有单测/代码属性，或现场根本没造出来 |
| **未验** | 一行子句都没有真机读数 |

三条硬规矩：

1. **证据指针必须指到节**，不是指到目录。写"见 P07"不算，要写 `run.log == 5. 挂载：UUID 两源核验`。
2. **状态按最弱的那一个子句定。** STAGES §19 的一行常常是三件事（"证书、私钥、WebSocket"），
   两件验了、一件没验，就是**部分**，不允许写成已验再在括号里小声补一句。
3. **本文件不引入任何新读数。** 每个数字都来自它指的那个文件；读不对就是这份文件和证据之间对不上，
   以证据为准，回来改这份文件。

判据量级沿用账本的三档：**真机**（Ubuntu 客机上的真实系统）＞ **单测**（宿主机或客机上的 Go/web 用例）
＞ **不支持**。**单测通过不计入"已验"**，这条在全表里执行到底。

### 2.1 DISK-02（根盘在 LVM/RAID 下 → 递归保护）—— 2026-10-29 闭环

初判**部分**，理由是结构性的：**"根盘在 LVM/RAID 下"这个现场从来没造出来过。** 递归保护在"系统盘"
这一层有真机证据（`P07/2026-10-21-p07.1/p07-1-acceptance-2404.txt` §3 的分区/格式化一律拒绝、
§8 的 dm holders、§9 的设备身份），但在"LVM/RAID 根"这一层没有——两者不能互相顶替，因为叠层根盘上
"哪个才是不能碰的底层盘"要先顺着 PV/VG/LV 或 md 成员往上追，那条路径没有现场跑过。两处账本自己
也这么写着（`P04/2026-10-20-p04.2/result.md:93`、`P07/2026-10-21-p07.1/result.md:190`）。

**2026-10-29 造了两台根在叠层设备上的 Ubuntu 24.04 客机，两场都过。** 都不是装出来的（`H:\Code\vms\images\`
只有 cloud image，没有 server installer ISO，subiquity 的 `layout: lvm|raid` 走不通），是**在客机里把根
迁过去**造的：第二/三块虚盘 → PV/VG/LV 或 `mdadm` → mkfs → `rsync` 整个根 → chroot `grub-install`
→ 摘掉系统盘重启。同一份脚本、同一批字节（`P16/2026-10-29-matrix/disk02/binaries.txt`）。

* **反证**：`sda1`（LVM 场）与 `sda1`/`sdb1`（RAID 场）都是 bios_grub 分区、同样在那块盘上、同样没有
  文件系统，但**不在根链路上，所以 `system_disk=false`**。这条把"按盘染红"和"沿链递归"分开了——
  没有它，"受保护"仍然可能是"这块盘上有根"的粗略判断。
* **一条写错的验收期望被 RAID 场抓了出来**：脚本原来把锁断言写成"每一块底层盘"，在只有一根 PV 的

**不因为这一条改判"已验"就消失**。

### 2.2 FILE-02：ENOSPC 补上了，这一条现在是已验（2026-10-29 闭环）

原话是「VM 的 root 是 overlay，塞满会把宿主一起挂住……写时 ENOSPC 的错误映射，但**没有真机证据**」。
另外「超大上传」在 P06.2 上是**按声明拒**（413），并没有真推 2 GiB 进去。

STAGES §19 对这条的期望是三句：**流式有界、清理暂存、不覆盖新版本**。逐句对上去：

| 期望 | 初判 | 现在 | 证据 |
|---|---|---|---|
| 流式有界 | 未验（`RESULT-measure` 里「上传 2 GiB 上限」NOT RUN） | **已验** | `P16/2026-10-29-matrix/gaps/2404-matrix-gaps.log` §6：2 GiB 真推，`200`、`received_bytes=2147483648`、**峰值 RSS 28740 KiB** |
| 清理暂存 | 已验（超限/不符不留暂存） | 已验，且补了写出错的那一路 | 同文件 §2（ENOSPC 后无 `.part`）、§3（断流后无 `.part`）；`P06.2` §4 |
| 不覆盖新版本 | 已验（`PREFLIGHT_STALE`） | 已验，且补了"失败上传不改目标" | 同文件 §2：失败的上传前后 `existing.bin` 的 sha256 不变；`P06.2` §6 |
| 触发场景「磁盘满」 | **未验** | **已验** | 同文件 §2：128 MiB tmpfs，声明 8 MiB（当时可用 131064 KiB）→ 填到只剩 512 KiB → PUT → **413 `VALIDATION_ERROR`「files: 空间不足」** |
| 触发场景「断流」 | 已验 | 已验 | 同文件 §3：`curl` 掐在 3 秒，代理记 `传输中断（已写入 3145728 字节）：unexpected EOF` |
| 触发场景「超大上传」 | 已验（按声明拒） | 已验（真的传完了） | 同文件 §6 |

三句期望现在都有读数，所以是**已验**。

两条要说清楚的话：

* **「并发编辑」这个场景是用强制交错复现的**（暂存期间外部改文件 → 提交 → `PREFLIGHT_STALE`），
  不是真竞态。判据落在「不覆盖新版本」那句上，那句有读数。真竞态在单机顺序脚本里制造不出可靠窗口，
  这一条留在 `docs/KNOWN_LIMITATIONS.md`，**不算验收缺口**（STAGES 的期望里没有它）。
* **ENOSPC 的现场尺寸是被代码逼出来的**：容量预检除声明字节外硬留 64 MiB 余量
  （`internal/files/staging.go:52` 的 `uploadReserveMargin`），所以小于 64 MiB 的根永远声明不了上传。
  16 MiB 的 tmpfs 试过一次，在声明阶段就被 413 掉，根本走不到写入——**测不到 ENOSPC**。
  这个过程记在 `gaps/README.md` §5。

### 2.3 APP-02：302 现场补上了，这一条现在是已验（2026-10-29 闭环）

初版判**部分**，理由也只有一条：**没有真机 302 现场。**「不跟随重定向」当时只是一条代码属性和单测，
`P09/2026-10-22-p09.2/run.log` 里既搜不到 `302` 也没有 `Location:` 夹具。

STAGES §19 对这条的期望是**拒绝**。三个触发场景逐条对上去：

| 触发场景 | 判据（「拒绝」落在哪） | 证据 |
|---|---|---|
| metadata 地址 | 候选的 `target_id` 形状根本表达不出 IP/主机/URL；写成 `169.254.169.254` 是 400，未发现的 id 是 422 | `P09/2026-10-22-p09.2/run.log` §3 |
| 外部主机 | 同上：候选**只能**由本机监听事实产生 | 同上一行 |
| 重定向探测 | 面板**不向 `Location` 里的地址发出任何请求** | `P16/2026-10-29-matrix/gaps/2404-matrix-gaps.log` §3 |

重定向那一格是本轮造的现场：两个真上游都回 `302`，一个指向回环金丝雀、一个指向
`169.254.169.254/latest/meta-data/iam/security-credentials/`。金丝雀把**每一次**命中都写日志，
所以"有没有跟过去"是个可以被数出来的事实，不是推断：

* 金丝雀命中 **0 次**（`payloads/upstream-hit-counts.txt`：`0 canary.log`，两个上游各 17 次）。
* 面板记录 `http_state=ok`、`status_code=302`，`address` 仍是 `127.0.0.1`，
  `url` 仍是 `http://127.0.0.1:19491/` —— `Location` 里的地址没有渗进记录。
* 指向 metadata 的那一个，记录里连 `169.254` 都搜不到。

**302 记成 `ok` 不是漏判。** `302` 落在默认成功集合里，含义是"这个站点能连上、能应答，
它选择用 302 回答"；面板如实记下状态码，不替人判断跳转目标好不好。**"拒绝"拒绝的是
"向那个地址发请求"，不是"拒绝承认 302 存在"** —— 这两件事混起来，就会把正确行为读成缺陷。

### 2.4 PROXY-02：不是"部分"，是本文件当初引错了证据（2026-10-30 更正）

初版把 PROXY-02 定成**部分**，依据是 `P10/2026-10-23-p10.2/run.log` 的 NOT RUN 段：
「WebSocket 握手实测：测试上游（python http.server）不支持 Upgrade；只验配置里 Upgrade/Connection 成对出现」。
**那句话本身没错，错在拿它当这一条的终点。** 同阶段的 P10.4 换过了上游，在两台机器上跑完了真握手：

## 4. 这份对照证明了什么、没证明什么

**证明了**：STAGES §19 的 31 条**没有一条是"从来没有被碰过"**，而且**一条"部分"都不剩**——
31 条都有完整真机读数，每一条都能顺着指针走到一个真实文件的具体一节。

**没有证明**：

* **不证明这 31 条就是全部风险。** §19 是"最晚阶段"清单，不是威胁模型；P16.3 的七维度复核
  （认证/权限/路径/命令/SSRF/设备身份/配置变更）是另一个方向的检查，两者不互相覆盖。
* **"每条都有读数"不等于"每条都没有残留的 NOT RUN"。** 矩阵按 STAGES 的子句判，子句之外还有
  一批明确写着"不验"的现场（臂 64 端到端、掉电语义、裸机开机到可用、根在叠层设备上写满、
  降级/重建中的阵列……），它们各自在 `docs/KNOWN_LIMITATIONS.md` 和对应证据文件的末节里，
  **不因为这一行改了状态就消失**。判据是"子句有没有读数"，不是"这台机器上什么都验过了"。
* **同一份证据改过断言，要读原文别只读结论。** DISK-02 的 RAID 场第一轮红过 5 条锁断言，
  查明是脚本期望写错（Q522），两份读数（`runs1-pre-fix/`）都留着；`RESULT-measure` 里那三条
  NOT RUN 也留原样，只是被别处的读数补上了。**划掉就是抹账。**
  （FILE-02 的 ENOSPC 与 APP-02 的 302 曾经也在这份名单里，2026-10-29 补上了真机现场，
  见 §2.2、§2.3；PROXY-02 是引错证据，见 §2.4；DISK-02 见 §2.1。）
* **`RESULT-measure` 里「文本编辑 1 MiB 上限」是相位错位，不是缺口**：它的原话是「属 P06 范围」，
  而 P06.2 §5 已经验过（`PASS 超过 1 MiB 的文本内容被拒（400）`）。
* **读数绑定的是它跑的那个字节。** 22.04/24.04 的 P16 读数是冻结字节 `3f3b40c1…daf0`；
  更早阶段（P02—P15）的读数是各自当时的字节。**跨阶段的读数不是同一份二进制**，
  矩阵说的是"这条能力在某轮被真实验过"，不是"这份 1.0 字节上又验了一遍"。
* **不替代 `docs/EVIDENCE_INDEX.md`**。那份按子任务索引文件清单，这份按 STAGES 编号索引断言；
  两份要一起看。也不替代 `docs/KNOWN_LIMITATIONS.md`——那边的每一条限制，要么对应一个曾经是"部分"、
  现在已闭环的条目（§2 的四条），要么对应一条子句之外的 NOT RUN（臂 64、掉电、裸机……），
  **两者都不是"已验"**。
