### 3.5 顺带发现：`DECISIONS.md` 第 8 节的 Q 表与自己的表头不一致（登记 Q521）

写本轮账本、准备补一条 Q 时，逐行数格才发现的事。表头（第 132 行）声明 5 列
（`编号 / 日期 / 类型 / 内容 / 状态·处理`），把 Q521 自身写进去后共 **521 条** Q 行。

按 GFM 规则重算（反斜杠转义的竖线算字面字符、不算分隔符），渲染后：

| 渲染格数 | 条数 |
|---|---|
| 5 格（与表头一致） | 458 |
| 4 格 | 1 |
| 6 格 | 54 |
| 7 格 | 4 |
| 8 格 | 1 |
| 9 格 | 1 |
| 10 格 | 2 |

不是 5 格的 **63 条**分三类：

1. **行内代码里的竖线没转义**：16 条、共 33 处（`Q40`、`Q44`、`Q113`、`Q136`、`Q137`、`Q138`、
   `Q140`、`Q155`、`Q159`、`Q233`、`Q298`、`Q300`、`Q315`、`Q364`、`Q378`、`Q420`）。写的是
   `O_RDONLY` 与 `O_NONBLOCK` 这类位或、`PREFLIGHT_STALE` 与 `CONFIRMATION_MISMATCH` 这类枚举、
   `gofmt -l .` 与 `wc -l` 这类管道 —— 一劈就多出格子。
2. **有意写成 6 字段**：46 条（`Q446`—`Q483`、`Q511`—`Q520`，P14.5 起把「内容」拆成
   现象 / 判定 / 处理），表头一直没跟着改。
3. **少格**：`Q14`（第 148 行）只有 4 格。

后果只落在渲染层：GFM 按表头列数截断，那 46 条的**最后一格（处理 / 已修）在预览里被静默
丢掉**，被劈开的 16 条整段错位。**原始 markdown 里字一个没少** —— 所以这是文档缺陷，不是
内容缺陷，Q521 里的判定也是这句。

**没修**，理由写在 Q521 里：先把列型定死再逐行转义，等于把 521 行账本重排一遍，属于文档
标准化任务，不在"矩阵对照"这个子任务里。**修之前引用任何 Q 号都得读原文，别只信渲染结果。**

读数可重跑：`check-decisions-table.py` → `facts-decisions-table.txt`。

**这条读数在 2026-10-30 之后又动过一次**：当天补的 `Q522`（写错的锁断言）与 `Q523`（本文档集
