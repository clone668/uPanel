# P16.2 补测：真机安装的面板 + 真浏览器（2026-10-27）

两台都跑了：`smoke.log`（22.04）、`smoke-2404.log`（24.04），都是 **35 PASS / 0 FAIL / 0 SKIP**。

## 为什么这份证据单独放

`tests/integration/p16-2-acceptance.sh` 的 `measure` 相位在 VM 内跑，VM 里没有浏览器
（干净 cloud image 只有 curl / openssl / python3），所以「浏览器完成主要用户流程」在
`RESULT-measure` 里记为 **NOT RUN**，理由写在相位日志里：
`VM 内没有浏览器；Playwright 隧道属另一份工件`。

这一份就是那件工件：**同一台 VM（VM-A）、同一份安装包、同一天**，面板在 VM 内以真实
安装方式跑起来，宿主机上的 Playwright 经 SSH 隧道把主要用户流程走一遍。
它补的是那一条 NOT RUN，不改变 `RESULT-measure` 里另外两条（上传 2 GiB、文本编辑
1 MiB，属 P06 范围）。

## 读数

`smoke.log` 全文，结尾：

```
PASS 35 / FAIL 0 / SKIP 0（共 35 项，production，目标 https://127.0.0.1:9443，已登录）
```

其中与本轮验收直接相关的几条：

* `未登录访问 / 落到登录页`、`未登录访问 /storage 同样落到登录页` —— 登录闸门在真后端上成立；
* `登录后回到被拦截的地址（/storage）` —— 登录后跳回原始地址，不是一律回概览；
* `导航包含已实现模块（…任务中心）`、`导航隐藏未实现模块（容器）` —— 导航与 `registry.ts` 的
  `implementedIn` 一致，容器仍是唯一未实现项；
* `概览页显示真实系统快照`、`概览页显示采集时间与刷新节奏（采集时间：2026/10/27 23:05:51（每 5000 毫秒刷新））`
  —— 页面上的数字来自代理，不是 mock；
* `存储页渲染到设备卡片（11 台）`、`设备详情页显示设备名（sda）`、`设备深链接不会落到"页面不存在"`
  —— 存储页对着真机的 `/sys/block` 渲染；
* `没有未捕获的页面异常`、`除预期的 401/404/503 外没有失败请求`、`没有其他控制台错误`。

## 24.04 那一台（Ubuntu 24.04.5 / kernel 6.8.0-147 / systemd 255 / 单线程 TCG）

同一份 `web/dist`、同一个脚本，`--base https://127.0.0.1:9443`，两次 **35 PASS / 0 FAIL**。
但拿到这两次之前，**四次失败**，每一次的原因都值得记下来——两次是我的错，两次是环境边界：

| 第几次 | 结果 | 原因 |
|---|---|---|
| 1 | 8 PASS / 1 FAIL（登录后跳转 20s 超时） | **我把隧道开在宿主 9444**，浏览器发的 `Origin: https://127.0.0.1:9444`，而面板只认 `listen_address` 推出的 `https://127.0.0.1:9443` → `POST /auth/login` **403**（产品行为正确：跨源必须拒） |
| 2 | 8 PASS / 1 FAIL（80s 超时） | 改回 9443 仍失败；journal 里是 `status=500`、`duration_ms=17355`、`error="读取二次验证状态失败: context canceled"` |
| 3、4 | **35 PASS / 0 FAIL** | 同样的命令、同样的机器，登录落在 15 秒内就全绿 |

第 2 次的 `context canceled` 不是服务端超时，是**前端自己放弃**：`web/src/api/auth.ts` 给登录请求设了
`timeoutMs: 15_000`。而同一份二进制在这台机器上一次登录要 **12—20 秒**（服务端 `duration_ms` 17.3s），
原因是密码哈希：`argon2id m=128MiB t=3 p=2` 在开发宿主（Apple M3）上实测 **128ms**，在单线程 TCG
的 24.04 客户机里一次登录烧掉 **9.5s CPU**（`/proc/<pid>/stat` 前后 947 ticks），放大约 **74 倍**——
内存硬哈希在模拟器上是重灾区。于是这条链路卡在"产品给了 15 秒、模拟器要 17 秒"的缝里。

**这不算产品缺陷**：15 秒对真实硬件是宽裕的（哈希 128ms），而"登录不能无限挂着"本身是对的。
**但它也不能被写成通过**：24.04 的浏览器读数按"两次成功、四次失败中两次是环境边界"如实记录，
并把它列进 P16.4 的已知限制——**在硬件虚拟化或裸机上重跑这一条之前，24.04 的登录时延不算验过**。

## 这份证据**不能**证明什么

* 不是"VM 内的浏览器验收"：浏览器在宿主机上，测的是 HTTP + 渲染层；
* 不覆盖上传 2 GiB 与 1 MiB 文本编辑（属 P06，另有读数）；
* 自签证书是**故意**放开的（`ignoreHTTPSErrors`），所以它不验证证书校验本身——
  证书指纹核对在 `install` 相位的断言里（`fp` 与 `RESULT-install` 一致）。

## 复现

```sh
# VM 内装好面板后，宿主上（端口必须与面板的 listen_address 一致，否则跨源 403）：
ssh -N -L 9443:127.0.0.1:9443 -i <key> -p 2223 upanel@127.0.0.1 &   # 22.04
ssh -N -L 9443:127.0.0.1:9443 -i <key> -p 2222 upanel@127.0.0.1 &   # 24.04
UPANEL_SMOKE_USER=admin UPANEL_SMOKE_PASS='…' \
  node web/scripts/smoke.mjs --base https://127.0.0.1:9443 --no-build
```

`UPANEL_SMOKE_TIMEOUT_SCALE=4` 是这一轮给脚本新加的**等待时间倍数**（默认 1）。加它的理由就是上面
那条：单线程 TCG 下登录要 10—20 秒，20 秒的 `waitForURL` 会在"登录还没回来"处超时，看起来像登录坏了。
它**只放大等待、不放宽断言**——等到了之后该出现的文字还得出现，慢环境不会因此变成通过。24.04 那两次
成功用的就是这个倍数（80 秒等待）；22.04 那次用的是默认值（不需要放大）。

面板是 22.04 那轮 `purge` 相位跑完之后**重新装的一份**（`/etc/upanel` 已在 purge 中删除），
所以 22.04 的证书指纹是那次新签的、与 `install` 相位那份不同；24.04 用的是归因探针那次重装的面板。
