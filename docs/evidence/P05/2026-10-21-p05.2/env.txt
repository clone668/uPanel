`CLK_TCK=100` 是本子任务的关键参数：`start_time_ticks` 就是 `/proc/<pid>/stat` 第 22 字段
（以 100 Hz 计的开机后滴答数），所以它的最小分辨率是 10 ms。验收里“同一个 PID 的
starttime 变了”指的就是这个数变了（30039 → 30049，差 10 个滴答 = 100 ms）。

### PID 重用是怎么做出来的

```
$ cat /proc/sys/kernel/ns_last_pid     # 可写，脚本才敢做这一步
printf '%s' "$((REUSE_PID - 1))" >/proc/sys/kernel/ns_last_pid
sleep 600 &                            # $! 必须等于 REUSE_PID，不等就 KILL 掉重试（最多 40 次）
```

脚本把 `ns_last_pid` 往回拨一个数，让内核把刚空出来的 PID 再分配一次。这一轮一次就命中：
老进程 `sleep 600` 的 starttime 是 30039，新进程是 30049——**同一个 PID、不同身份**。
用老预检提交得到 409 `DEVICE_IDENTITY_CHANGED`，而新进程在整轮验收结束时仍然活着
（这是本子任务的核心验收点：旧预检不能杀新进程）。

## 环境侧异常记录（必须一起看）

这台 VM 的 PID 1（systemd）在长时间运行后会 SIGSEGV，随后内核 panic。宿主上留下的
console 日志共 7 份（`H:\Code\vms\upanel-2404\`）：

| 文件 | 时间 | 情况 |
|---|---|---|
| `console.panic-2026-10-20.log` | 10-20 20:25 | 第一次 |
| `console.panic-2-2026-10-20.log` | 10-20 21:15 | 第二次 |
| `console.panic-3-2026-10-21.log` | 10-21 05:38 | 第三次 |
| `console.panic-4-2026-10-21.log` | 10-21 07:17 | 第四次 |
| `console.panic-5-2026-10-21.log` | 10-21 08:08 | 第五次 |
| `console.panic-6-2026-10-21.log` | 10-21 09:06 | 第六次（P05.1 记录的那次） |
| `console.panic-7-2026-10-21.log` | 10-21 10:17 | 第七次，触发本轮重启 |

第七次的现场（uptime 4256 s ≈ 71 分钟，P05.2 第一轮验收之后、第二轮之前）：

```
[ 4256.695456] systemd[1]: segfault at 771d97dfffb8 ip 0000727f5352a29f sp 00007ffc7cf453e8 error 44 in libc.so.6[727f53428000+189000]
[ 4256.709612] systemd[1]: segfault at 771d97dfffb0 ip 00005a978ac9ffdf sp 00007ffc7cf44e00 error 46 in systemd[5a978ac96000+b000]
[ 4256.779505] Kernel panic - not syncing: Attempted to kill init! exitcode=0x0000008b
[ 4256.783436] CPU: 1 PID: 1 Comm: systemd Not tainted 6.8.0-147-generic #147-Ubuntu
```

`error 44/46` 是 page fault 错误码里第 3 位（reserved bit）置位，属于“不该出现的
异常”，不是普通缺页。七次形态一致，只出现在这台 24.04 的 QEMU 上，且与 guest 负载
（跑不跑验收）没有稳定关系。

已排除的两条：

- **不是镜像共享**：三个 QEMU 进程是三台不同的 VM（各自的磁盘与 console），不是同一份镜像被
  并发写。
- **不是宿主内存不足**：宿主 63.9 GB 总内存，panic 发生时仍有 32.4 GB 空闲。

未定位。处理方式：第七次 panic 后重启（宿主 10:21:37 启动 QEMU 26908），guest 在
02:21:42Z 起来；**第二轮验收在 02:26:24Z 采集第一批快照**，即重启后 5 分钟，本目录所有
结果都来自这一次 boot。若后续再出现同类 panic，先看新的 console 日志，再决定是否重建 VM。

## 这台机器上没有的东西（影响 NOT RUN 的判定）

- **没有浏览器**：进程页面的像素证据不在 VM 上取，改为宿主上用同一批载荷做 SSR 回放
  （`web/src/components/realdata-processes.test.ts` 读 `web/src/fixtures/p05-2-vm/`，
  22 个文件与 `payloads/` 里那 22 个逐字节相同，已用 `cmp` 核过）。
- **没有 Go / Node**：所有二进制在宿主交叉编译（`GOOS=linux GOARCH=amd64 CGO_ENABLED=0`）。
- **D 状态 / 忽略 SIGTERM 的进程造不出来**：TERM 超时与 KILL 后仍存在这两条只在
  `internal/processes/signal_test.go` 的 fake 里覆盖，VM 上标 NOT RUN。
