P11.3 验收环境（2026-10-23，第 2 轮）
====================================

证据类型：**Linux VM integration（两台真实 Ubuntu、真实 systemd、真的重启、真的断电，
由宿主机在机器"死掉"之后重新上电）+ 宿主 `scripts/check.sh`**。
不含浏览器渲染：验收 VM 上没有浏览器，页面（`PowerControlCard` / `PowerCheckPanel` /
`JobsView`）只有类型检查、组件逻辑与真机 JSON 回放，没有在浏览器里点过——记在 result.md
的限制里。

这一份是**第 2 轮**。第 1 轮（同一天早些时候）的产物已经整份作废，不是"覆盖"，是重跑：
22.04 的阶段二出了 6 条 FAIL，全是 `GET /system/power-state` 返回 503
（`AGENT_UNAVAILABLE`）。查清楚之后发现根因有两个，一个在环境、一个在产品，都已修
（见 result.md「第 1 轮那 6 条 FAIL 的根因」）。第 1 轮的日志曾用于证明那两个缺陷是真的，
随后被第 2 轮替换。

这条子任务的验收条件是两句话：「关键任务运行时拒绝电源操作；关机界面不伪称已验证」。
它的难点不在代码而在**证据位置**：脚本与被重启/被断电的机器是同一台，机器一死，
脚本就写不了自己的结论。所以脚本拆成三段进程：

    --phase pre    拒收面、预检、在跑任务拒绝、取消、下发 reboot（60 秒倒计时）
                   → 观察窗内断言"还没重启"，然后把自己交出去
    （机器真的重启）
    --phase post   用 boot_id 确认那次重启真的发生过，读 reboot 任务的终态，下发 poweroff
    （机器真的断电，QEMU 进程消失）
    （宿主机重新上电）
    --phase final  读 poweroff 任务的终态，核对"关机"能说什么、不能说什么，审计
    --phase report 汇总 logs/results.txt

倒计时之所以是 60 秒而不是默认的 30 秒：30 秒会和脚本自己的观察窗（25 秒）挤在一起，
第一次跑时脚本正在 `wait_job` 里等状态，机器就在它脚下重启了，日志戛然而止。

环境干预（必须写清楚，否则"PASS"是假的）
----------------------------------------
① **两台上都有外来的 upanel 系统服务**：`upanel-agent.service` / `upanel-web.service`，
   是早前一次安装验收留下的，`ExecStart` 指向已经被删除的
   `/usr/local/lib/upanel/upanel-agent`，`Restart=on-failure` 于是每 3 秒重生一次
   （22.04 上 `NRestarts=116`，`status=203/EXEC`）。它们带 `RuntimeDirectory=upanel`，
   **每停一次就删掉 /run/upanel**——里面正是脚本手启的代理的 socket。
   处理：`systemctl disable --now` + 把单元文件改名挪走（`*.disabled-by-p11-3-acceptance`）
   + daemon-reload；脚本里的 `guard_foreign_units` 每阶段再断言一次"一个都不剩、
   `is-active` 只能是 inactive/failed/unknown"，否则 exit 2 认定环境不满足。
   这条断言本身就是 §0 的 `env-no-foreign-units`（两台各一条 PASS）。

② **24.04 的"重启"环节是宿主冷启动，不是客户机热重启**（本轮最重要的一条限制）。
   QEMU 11.1.0 + WHPX 在这台宿主上**无法完成客户机 reset**：guest 打印
   `reboot: Restarting system` 后 QEMU 卡住，stderr 是
   `WHPX: Unexpected VP exit code 4`，串口不再增长（本轮 4 次尝试，4 次挂住；
   第 1 轮同样配置下曾成功过两次，所以这是**时好时坏**，不是必然）。
   串口原文留在 logs/2404-console-reboot-hang.log。
   处理：确认 guest 已经到达 `reboot.target`（文件系统已 sync、systemd 已把
   shutdown 走完）之后，宿主 kill 掉卡住的 QEMU 再冷启动。机器的 boot_id 确实变了，
   阶段二的断言全部照跑；但**"客户机自己回来"这一环在 24.04 上没有验到**，
   只有 22.04 验到了（它真的自己重启回来了）。result.md 的限制②写明了这一点，
   不许把它读成"两台都验到了客户机热重启"。

③ **22.04 的断电串口日志没留下**：它的 `console.log` 在宿主重新上电那次启动时被覆盖了
   （`-serial file:` 是 truncate 打开）。22.04 的"真的断电"证据因此只剩三样：
   阶段二日志结尾的 NOT RUN 说明、重新上电时 2223 端口曾连接被拒（旧 QEMU 已退出，
   新 QEMU 才能 bind 同一个 hostfwd 端口）、以及阶段三读到的新 boot_id。
   24.04 的串口日志这次保住了：logs/2404-console-poweroff.log 结尾是
   `reboot: Power down`。这是操作失误，不是产品问题，但记录里不能装作两台一样整齐。

真机上的坑（都会伪装成"产品坏了"）
----------------------------------
① `fs.protected_regular`：/var/tmp 是 sticky 目录，root 也不能 truncate 别人（upanel 用户）
   创建的文件。`sudo sh -c "... > /var/tmp/x.log"` 里的重定向由外层 upanel 用户执行，
   于是 Permission denied、ssh 那端立刻退出，而等待器读的是**上一轮留下的**同名日志。
   修法：日志一律写进 root 自己的 /var/tmp/upanel-accept-p11-3/logs/，并且
   **先看 mtime 与行数再信内容**。
② 脚本自建的 trap 会杀掉自己要验的东西：阶段一/二结尾必须 `KEEP_SERVICES=1`。
   第一次没设，trap 在退出时把代理优雅停掉，倒计时里的 reboot 任务变成 `interrupted`，
   机器根本没重启——脚本踩掉了自己的现场。
③ 外来的 systemd 单元（见上 ①）：不只是抢端口/socket，还会在别人的目录里做
   `RuntimeDirectory` 清理。这类故障在面板上只表现为"代理不可用"。
④ QEMU 的加速器与发行版是**交叉绑定**的：这台宿主上 22.04 只能用 tcg（whpx 挂死），
   24.04 只能用 whpx（tcg 开不了机）。换机器要重新试，不要照抄。
