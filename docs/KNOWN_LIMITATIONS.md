# 已知限制（uPanel 1.0）

这份文档只做一件事：把"这一版**不**是什么"说清楚，让用户在故障现场不用猜，
也让下一个人接手时不必从 8000 行进度账本里挖。

三种东西混在一起会互相削弱，所以先分开：

| 类别 | 含义 | 你该怎么做 |
|---|---|---|
| **A. 未验证** | 功能写了、单测过了，但没有真机读数 | 别把它当已验收；当作"可能会坏"的功能先用一次 |
| **B. 有意的边界** | 产品明确不做，做了会变成另一种产品 | 别指望，找替代方案 |
| **C. 容易误解的语义** | 功能是对的，但"它到底证明了什么"和直觉不同 | 读这一节，尤其是报警和备份相关 |

## A. 未验证（有代码、没真机读数）

**这条清单和 `docs/ACCEPTANCE_MATRIX.md` 是一套的**：那边按 STAGES §19 的 31 个编号定档（**已验 31 / 部分 0 / 未验 0**），这边按「没什么读数」列。**两份不是同一把尺子**：矩阵量的是"那 31 条子句有没有真机读数"，这份量的是"这个系统还有哪些地方没人量过"。矩阵一条"部分"都不剩，不等于这份清单清空——下面这些大多落在子句之外（臂 64、掉电、裸机、0.1→1.0 升级……），STAGES §19 从来没要求过它们，但它们同样没被验证。

## B. 有意的边界（不会做）

| 边界 | 为什么 |
|---|---|
| **面板自己没有"用户管理"页面，也没有"改密码"入口** | 1.0 只能通过 HTTP API（`POST/PATCH/DELETE /api/v1/users`、`POST /api/v1/users/:id/password`）管理 admin/viewer 账号与口令，界面上只有 TOTP 那一页。改自己的口令用 `upanelctl reset-password`（本机 root）或那条 API（管理员 + 再认证）。功能在、界面缺；不拿别的页面去占这一格 |
| 单机 | 一台服务器，面板与代理同机；不做多机/集群 |
| 网络只写 IPv4 | 桥接、bond、VLAN、Wi-Fi、IPv6、NetworkManager 都只读；PLAN 第 19 节 |
| 只支持 systemd-networkd | 不替换整份 netplan 去赌，只写面板自己那一份文件 |
| 防火墙只支持 UFW | 检出 nftables/iptables 混用时整体只读，绝不混写两套规则 |
| 卷只接管 ext4 / XFS 普通分区 | LVM/RAID/swap 只识别与保护，不创建、不扩容 |
| 格式化**没有**恢复路径 | PLAN 明确写了；只能靠你自己的备份 |
| 备份后端只有 `local` 与 `sftp` | restic 支持更多，面板不做（key、S3 等不在范围） |
| 面板自身不做在线升级 | 升级是"停服务 → 备份 → 换二进制 → 迁移"的手工流程，见 INSTALL.md §7 |
| 不做 ACME 给面板自己签证书 | 自签名（安装时打印指纹）或用户提供 |
| 不接受任意 sudoers 文本 | 只允许固定模板 + `visudo` 校验 |
| 不通过 Web 给面板账号 sudo | 也不绕过终端限制 |
| 没有通用命令执行 / 任意 root shell | 路由名与动作表都不允许 |
| 登录限速是进程内计数 | 重启清零、不跨进程共享（PLAN 第 5 节的取舍）；不落库 |
| SSRF 不做内网地址黑名单 | 管理员配置的就是内网目标；加黑名单只砍功能，不增安全 |

## C. 容易误解的语义

这一节最值得读。每一条都写得像"限制"，其实是在说"这个字段只证明了这一点"。

### C1. 健康探测只证明"宿主端口能应答"

`http` 只判状态码落在 200—399。一个返回 200 的错误页算"健康"，一个返回 500 的可用首页算"不健康"。
`tcp` 只证明端口能连上。这是健康检查的固有边界，不是缺陷——但页面上写"健康"时，要知道它说的是哪一件事。
`exec` 类健康检查不在契约里（面板不知道镜像里有什么命令）。

### C2. 备份成功 ≠ 恢复可用

`backup.run` 成功只说明 restic 退出码为 0 且快照存在。要证明"能恢复"必须跑 `backup.verify` 的抽样恢复，
而抽样恢复证明的是"抽到的那几个文件能读出来"，不是"整个快照能完整还原到一台干净机器上"。

### C3. `unit_restarted` 说的是"我怎么交的班"

它为 `true` 只表示这一轮用的是 `restart` 而不是 `start`，**不表示**容器真的换了一个。容器是否真换了，
要靠 `docker inspect` 的 ID 与 `StartedAt` 另证。

### C4. `managed` 不等于依赖被接管

`managed` 只说"经面板发起的启动会被依赖卷门禁检查"。手工 `docker start`、开机自启、
`systemctl enable` 过的单元、`restart: always` 这四条路都绕过面板，因此这类一律标 `unmanaged`
并在说明里点名是谁绕开了。运行期卷掉线**不会**自动停已跑的容器（拦的是"下一次经面板的启动"）。

### C5. nginx 的"已验证"不等于"新连接一定用新配置"

`verified` = 落盘 + 读回 hash 一致 + 单元 active + `reload` 完成。`nginx -s reload` 返回后 6—111 ms 内
新配置才开始应答，连续 reload 时 20 次里有 7 次仍被旧 worker 应答。**不要**用瞬时读数判断"配置没生效"。

### C6. 应用"在线"不等于配置生效

运行状态来自采集器快照（默认 10 秒一轮）。刚发完 `service.control`/`container.control`，
摘要还会说着上一轮的事实——页面如实画它读到的那一轮，不做乐观更新。

### C7. 回切不回切数据

部署回切只回切配置与镜像。有数据库迁移的应用，新版本动过的数据旧版本读不了；这一版**没有任何检测手段**
能提前发现"这次更新会动数据"。`.prev` 只有一份，连续两次更新之后回不到上上版。

### C8. 备份预算 360 秒

更新前备份刻意只给 360 秒（且只收 `files_only`）。数据量大的应用几乎一定超预算——那就先单独跑一次
`backup.run` 再更新。反过来（让更新安静跑四十分钟、最后把应用留在停止状态）更糟。

### C9. 数字类上限（都会被当成"限制"报上来）

| 项 | 上限 | 超了会怎样 |
|---|---|---|
| 指标原始样本 | 5 秒一个点，24 小时保留 | 约 **30 MB/天** 的库增长；之后按分钟/小时粒度滚存 |
| 日志查询 | 单页 ≤ 1000 行 / 1 MiB，窗口 ≤ 24 小时 | 服务端拒绝并说明，不截断后假装完整 |
| 软件包列表 | 每页 200 条 | 731 个包要翻 15 页；没有全量导出，也没有服务端搜索索引 |
| 文件写入 | 1 MiB、UTF-8 | 拒绝（上传走暂存，另有上限） |
| 终端 | 数量、时长、一次性许可 | 到限即断，不静默续期 |
| 电源操作 | 延迟 30—300 秒 | 超出范围拒绝 |

### C10. 密码校验比直觉慢

Argon2id 在 2 vCPU 虚机上（TCG 模拟）实测要数秒，而 CONTRACTS 写的是 100—300 ms。真机会快得多，
但**在模拟器上登录会撞到前端 15 秒超时**——这是环境问题，不是产品缺陷；参数标定不在 1.0 范围。

### C11. 版本号与迁移方向

数据库迁移**只向前**：`upanelctl migrate` 发现"库里的 schema 比二进制新"会拒绝运行。
用旧二进制回退必须同时恢复数据库备份，1.0 不声称支持自动降级。

### C12. 任务执行期间读部署现场可能超时，页面会短暂显示"代理不可用"

部署现场（`GET /api/v1/deployments/managed*`）是**现算**的：每份部署都要问一遍 systemd、
读一遍配置目录。任务正在跑（尤其是首次拉镜像那种重 I/O）时，这台机器上的读查询会变慢。

面板到代理这条调用用的是通用上限 10 秒。**超时会被报成 `AGENT_UNAVAILABLE`（503
"代理不可用"），实际是"代理答得慢"**——页面下一轮轮询就会自愈，但要改成"代理超时"得先动
错误分类，1.0 没动（Q512）。

P15.4 的单线程 TCG 验收机上实测到过两次（面板侧 10008 / 10025 ms，同一时刻代理侧
`status 200, duration_ms 10020 / 10037`——代理答了，只是答在 10 秒之后）；镜像已在本地的那一轮
57 条请求全 200/202，最长读 6470 ms。真实 2 核以上机器不应该顶到这个上限。

### C13. 浏览器放弃的请求会被记成"服务端故障"/"代理不可用"

页面导航或组件卸载时，浏览器会 abort 掉还没回来的请求。这时面板到代理的调用以
`context canceled` 收尾，但日志与状态码会把它翻译成别的东西：

- 会话校验层：曾记成 `ERROR 会话校验失败` + 对外 500 `INTERNAL_ERROR`；
- 读查询层（存储、系统信息、容器、应用发现……）：记成 `WARN …：代理不可用` + 对外
  503 `AGENT_UNAVAILABLE`。

这些响应**没有任何人收到**（请求方已经走了），但日志里留下的是"服务端坏了""代理不可用"。
后果只有一个：读日志的人（和做验收的人）会去追一个不存在的故障。数据与页面都不受影响。

**1.0 只修了会话校验那一层**：取消的请求现在记 `WARN 客户端已断开，会话校验中止`，
状态码是 nginx 惯例的 499（没人接，只是让访问日志说实话）。读查询那一层的"取消 vs 不可用"
判定还在 `agentclient` 里，要改它得同时动十来个领域包的分类用法，1.0 不动（Q514）。

在 P15.4 的最终字节上实测到一次（三条请求，同一秒内），复现实验与排除项见
`docs/evidence/P15/2026-10-28-p15.4/client-canceled-misclassified.txt`。

## 证据位置

上面每一条的原始读数都在**仓库**的 `docs/evidence/` 下，按阶段分目录。这两份文件不随发布包
发出（它们是仓库的一部分，包里的 `docs/` 只有安装与使用相关的那十份）：

- `docs/EVIDENCE_INDEX.md`：全部证据的索引（哪个子任务、哪份目录、什么类型的读数）。
- `docs/PROGRESS.md`：逐子任务的账本，第 5 节是现场描述，第 8 节是已知限制。

也就是说：**装机现场能查的是"这一版不承诺什么"，查"凭什么不承诺"要回到仓库。**
